## 0. 守ること（最優先）
- 進捗は事実で語る。「画面に完了と出た」は証拠ではない。証拠は GitHub のコミット + Supabase の `publish_commit_sha` / `publish_verified_at` / `published_url`。
- 動いていないものを「バックグラウンドで動いている」と言わない。実行していないことは「まだやっていない」と書く。
- 店長の確認は最小限。ただし、本番公開・本番デプロイ・費用が増える操作は、店長の承認を取る。
- 決まっていないことを決まったように進めない。分かっていないことを分かったふりをしない。
- 呼び名: ユーザーは「店長」。「社長」はオーナー（別人）。

## 2. 毎週の改善（PDCA）
1. 取得: Search Console の「ページ」「検索クエリ」を**直近28日**で取得（当面は店長がCSVを書き出す。記事別の自動取得は今後追加）。
2. 取り込み: URL を正規化（`#…` `?…` を除く、末尾スラッシュを統一、重複は合算）。`/blog/` `/blog/page/N/` `/blog/category/` は除外。
3. 分類（順に判定。しきい値は【仮】）: 表示<20→保留 / 平均順位11〜30→C あと一歩 / 表示≥100 かつ CTR<1%→B / 表示<100 かつ CTR<1%→E 様子見 / それ以外→D 良好。
4. 提案: 1週間に直す記事は**最大3本**。1本につき変更は**1種類**（タイトル、説明文、サムネイル、導入、のどれか）。
5. 記録: `43_BLOG_IMPROVEMENT_LOG` に、変更前後・仮説・公開日・判定日（公開日+28日）を残す。
6. 判定: 変更の28日後。表示20回未満なら判定しない（保留）。
- 3回は手動で回し、手順に無理がないと確認してから自動化する。

## 3. 記事の候補（毎日3案）
- 数は3案。理由と根拠を付ける。選ぶのは店長。選択前は制作しない。
- 配分: トレーニング系と SEO 向けをメインにする。酸素・DENBA も主力商品なので外さない。ボクシングも定期的に出す。**均等にはしない**。
- 直近の公開記事のテーマ内訳を数え、偏りがあれば他テーマへ振り分ける。
- 各案に添える根拠: 直近の公開テーマの内訳 / `42_BLOG_PERFORMANCE` の同テーマ実績（表示・クリック・平均順位。集計期間を併記。無ければ「実測なし（仮説）」）/ SEO上の狙い。数字を作らない。
- SEO 向けの候補を毎回1案程度入れる。
- 実績が B または C の既存記事は、新規より先に改善候補として最大3本まで一緒に出す。

## 4. 画像（サムネイル）
- 生成: GitHub Actions `auto-editorial-hybrid-images` が OpenAI API を呼ぶ（鍵は GitHub Secrets。Claude は直接呼べない）。ジョブは `editorial/hybrid-image-jobs/` に置く。
- 品質チェック（QC）に不合格なら、**最大3回まで自動で作り直す**。店長が見るのは合格した画像だけ。3回とも不合格なら失敗として止めて知らせる。
  - 現状のコードは再生成を1回に固定している（`scripts/auto-editorial-hybrid-image.mjs` の MAX_TOTAL_ATTEMPTS）。3回化は未実装。実装前にこの記述を現状に合わせて更新すること。
- 3回で足りるかは運用して見直す。作り方が固まれば、2回・1回で済むようにする。
- 画質は費用と質を見て決める。現状は medium。同じ記事で high と比べて決める。
- 1つの生成画像を、サムネイル・OGP・GBP の3形式にレイアウトで使い回す（形式ごとに別生成しない）。
- 費用: 画像を作るたびに概算費用を記録して店長に共有する（記録先はマスターシートに追加予定。未作成）。上限は最初はかけない。過去に月8,000円分の想定外の請求があった（原因は未特定）。OpenAI管理画面で月の上限と通知を設定することを店長に依頼済み。
- 承認なしに、OpenAI 以外の画像生成サービスへ送らない。

## 5. 公開の流れと証拠
- 流れ: 管理画面 `/admin/articles/` → 下書き保存（Supabase `admin_article_drafts`）→ Review & Publish → `api/admin/publish.mjs` → GitHub `content/blog/{slug}.md` → GitHub Actions「Deploy to Xserver」→ 反映の確認。
- 公開済み記事を再公開する時は、編集画面から入る（`from=editor`）。
- GitHub のファイルを直接編集すると、Supabase の下書きとずれる。直接編集したら、その旨を下書き側へ反映する。
- 本番の Vercel デプロイは `VERCEL_RELEASE_POLICY_V1.md` に従う。docs だけの変更ではデプロイしない。

## 6. モデルの使い分け（Fable / Opus / Sonnet）
- Fable は、本当に考察が必要な所だけ（方針の設計、原因不明の不具合、判定の難しい品質評価）。
- それ以外（取り込み、集計、定型の記録、確認作業）は Sonnet 等で足りる。
- 最終の品質検査だけ、上位モデルを使う想定。
- どのモデルでも、このプロトコルを同じように守る。
