## 1. 全体の流れ（新しい仕組み）

```
[GitHub Actions: column-morning.yml]  営業日（火水木土日）05:30 JST ／ 07:30 は失敗時だけの再実行枠
        │  ※PCが切れていても動く（GitHubのサーバーで実行）
        ▼
 prepare ─ ① 営業日・重複チェック（column_auto_runs に1日1行。DELIVERED なら何もしない）
        │  ② 費用チェック（今月の累計＋1回分の上限が月の上限を超えるなら停止して通知）
        │  ③ テーマ選定
        │     Search Console（28日・記事別/検索語別）→ 分野ごとの実績で倍率を更新（PDCA）
        │     → 配分（トレーニング30/SEO健康22/ジム選び14/酸素12/DENBA10/ボクシング12）と直近20本の偏り
        │     → 酸素・DENBA・ボクシングは10本に1本以上、同じ分野の3連続は避ける
        │     → Sonnet が候補5つ → 重複・店長しか知らない事実が要る案を除外 → 1つ採用（理由を記録）
        │  ④ 執筆（Opus 5.5）→ 機械チェック（店名・絵文字・言い切り表現・文字数など）
        │     → 別のチェック役（Sonnet 5.5、迷うものだけ Opus 5.5）が合否 → 不合格なら書き直し（最大3稿）
        │  ⑤ 画像ジョブを作成して main に記録
        ▼
 images ─ 既存の Hybrid 画像（auto-editorial-hybrid-images.yml を workflow_call で呼ぶ）
        │  生成: OpenAI gpt-5.6（変更なし）／判定: Claude が画像を直接見る（Sonnet、迷うものだけ Opus）
        │  最大3回まで作り直し → 合格したものだけ Xserver に配置・バイト一致を確認
        ▼
 finalize ─ ⑥ ストーリー画像（1080×1920、上に見出しだけ・下の白枠は空）→ Claude が判定（最大3回）
          ⑦ 公開前チェック（validateDraftForPublish）→ 管理画面の下書きに保存 → 読み戻して NOT_PUBLISHED を確認
          ⑧ 22_GBP_POST と 44_COLUMN_TOPIC_LOG に1行ずつ記録（店長はシートを開かなくてよい）
          ⑨ 店長への受け渡し: private リポジトリ the-rev-ops の Issue
             （サムネ・GBP画像と投稿文・ストーリー画像と枠の文言・UTMリンク・リンクスタンプ文言・API別の費用）
```

公開は**自動では一切しない**（公開APIを呼ぶコードが無いことをテストで確認）。

## 2. 直したこと

| 内容 | 理由 |
|---|---|
| 画像の判定を OpenAI → **Claude（B案）** に変更。Sonnet が判定し、点数が境目（7〜8点・人物の占有率が境界付近・自信が低い）のときだけ Opus で二次確認 | ご指示。OpenAI の判定が1回あたり約$0.12と高く、作り直しのたびに2回呼んでいた |
| Hybrid 画像の毎朝の cron（06:00）を削除し、朝の実行から呼ぶ方式に一本化 | 起動の経路が2つあると二重実行・空振りの原因になる |
| 判定回数の上限を 1試行2回 → 4回（二次確認の分）。通常は2回のまま | 二次確認で上限に当たって止まらないように |
| 既存の検証スクリプトを新しい起動方式に合わせて更新 | |

### 失敗したときの動き
- 一時的な失敗（API の混雑など）→ 07:30 に1回だけ再実行。2回目も失敗したら Issue で知らせて止まる
- 品質チェックに3稿とも不合格・画像が3回とも不合格・費用上限 → **再実行しない**（無駄な費用を防ぐ）。Issue で知らせる
- 同じ日に記事を2本作らない（日付ごとの行と `editorial_content_id = COL-YYYYMMDD` で二重に確認）
- LINE は「店長しか知らない事実が要る候補」が出たときだけ、同じ質問は1回だけ送る（その日の記事は別テーマで進める）

## 4. 費用

### 4-1. 9〜10月の約8,000円/月の原因調査
- GitHub Actions の実行履歴 2,292件を確認。実際に画像を生成した重い実行は **9月: push 12回＋3回、10月: push 22回＋schedule 1回＋dispatch 1回、11/4: push 2回＋dispatch 2回**
- 1回の試行 ≒ 生成1回＋OpenAI判定2回（判定1回 約1.8万入力/2〜3千出力トークン ≒ $0.12）で **約60円**、3回作り直すと **約180円**
- 9〜10月の重い実行 約40回 × 1〜3試行 ≒ **5,000〜8,000円** → **最も可能性が高い原因は「画像の作り直し×OpenAI判定のループ」**（新しい asset_version で再実行すると回数の上限がリセットされていた点も増幅要因）
- 15分ごとの cron（9/24〜9/29）は空振り（生成なし）で原因ではない。GITHUB_TOKEN のコミットは再起動しないのでループもない
- 参考: GAS の `DAILY_TOPIC_POOL` が10/23頃から毎時（5時〜24時）失敗し続けており、毎回 OpenAI を呼んでいる可能性がある（**未確認**）
- 正確な金額は **未確認**（OpenAI の管理画面の Usage でしか確定できない）

## 6. 店長にお願いすること（ここだけは店長しかできません）

GitHub の `the-rev-website` → Settings → Secrets and variables → Actions → **New repository secret** で登録:

| 名前 | 中身 | 用途 |
|---|---|---|
| `ANTHROPIC_API_KEY` | Claude の APIキー（console.anthropic.com） | 執筆・チェック・画像判定 |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Project Settings → API → service_role | 下書きの保存・実行記録 |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | Googleのサービスアカウントの鍵（JSON全体） | Search Console の取得とシートへの記録。**そのサービスアカウントのメールを、マスターシートに「編集者」で共有**し、Search Console にもユーザー追加 |
| `COLUMN_DELIVERY_TOKEN` | GitHub の Fine-grained token（対象: the-rev-ops、権限: Issues = Read and write） | 毎朝の受け渡し Issue |
| `LINE_CHANNEL_ACCESS_TOKEN` / `LINE_USER_ID`（任意） | 公式LINEのトークンと店長のユーザーID | 店長しか知らない事実を聞くときだけ |

`SUPABASE_URL` と `ADMIN_PUBLISHER_USER_ID` は秘密ではないので、AI側でリポジトリの変数として登録済み。
